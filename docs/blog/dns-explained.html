1. What DNS is

Computers connect to IP addresses (like 203.0.113.10 or 2001:db8::10). People type names (like www.example.com). The Domain Name System is the internet-wide, distributed database that turns one into the other. Every time you open a site, an app syncs, or a smart TV checks for updates, a DNS lookup almost certainly happened first.

A DNS answer is made of records. Each has a type, a value, and a TTL (time to live: how many seconds anyone may cache it). The ones that matter here:

TypeQuestion it answersExample
AIPv4 address for this name?www.example.com → 203.0.113.10
AAAAIPv6 address for this name?www.example.com → 2001:db8::10
CNAMEIs this name an alias for another name?www.shop.example → shop.cdn.example
NSWhich servers are in charge of this domain?example.com → ns1.dns-host.example
HTTPSHow should I connect (HTTP/3? keys)?Asked by modern browsers alongside A/AAAA
MX, TXT, PTRMail server, free text, reverse lookup (IP → name)Email, verification, logs

(Addresses in this post are illustrative, taken from ranges reserved for documentation.)

The database is split into a hierarchy, read right to left. Nobody holds all of it; each level only knows who is in charge of the next level down.

2. How a name gets resolved

There are two kinds of DNS software in this story:

  • A stub resolver: the small client built into your OS (and some apps). It doesn't know how to walk the tree; it just asks one configured server and waits.
  • A recursive resolver: a server that does the walking: root → top-level domain → the domain's own nameservers, caching everything along the way. Your ISP runs one; so do Cloudflare (1.1.1.1), Google (8.8.8.8), and Quad9 (9.9.9.9).

Step through a cold lookup (nothing cached anywhere), then switch to the cached scenario to see why the internet isn't drowning in DNS traffic.

Caching is the whole trick. Root and .com referrals are cached for days, popular answers for minutes. Your browser, your OS, and every resolver along the way keep their own cache, so most lookups are answered in a millisecond without leaving your house. It's also why a DNS change can take a while to "show up".

3. How devices, phones and browsers use DNS

Normally you never pick a DNS server. When a device joins a network, the router tells it which one to use: DHCP hands out a DNS address for IPv4, and IPv6 router advertisements (or DHCPv6) do the same for IPv6. Most home routers point you at themselves, and they forward to the ISP.

That default is increasingly not what actually happens, because several layers can override it:

  • Manual DNS on a device's network adapter replaces what the router handed out (what I do on my PC).
  • Browsers can skip the OS entirely with DNS over HTTPS (DoH): Firefox calls it TRR, Chrome calls it Secure DNS. Lookups go encrypted straight to a provider like Cloudflare.
  • Android "Private DNS" uses DNS over TLS (port 853) to a provider you choose, ignoring the Wi-Fi's DNS.
  • iPhone iCloud Private Relay sends Safari's traffic, DNS included, through Apple's relays.
  • Some apps and smart TVs hard-code a public resolver like 8.8.8.8 and ignore your settings completely.

This matters for anything that filters by DNS (parental controls, Pi-hole, school networks): a filter only sees the lookups that are actually sent to it. Every encrypted or hard-coded path above walks straight past it.

4. Visiting a website: DNS is only step one

Once the browser has an address, four more things happen before you see a page:

  1. Connect. TCP (or QUIC for HTTP/3) to the address on port 443. On the way out, the home router swaps your private address for your home's single public IP (NAT).
  2. TLS handshake. The browser names the site it wants (SNI, sent unencrypted in most cases). The server answers with a certificate for that name, signed by an authority the browser trusts. If it checks out, everything after this is encrypted.
  3. HTTP request. Only now does the path (/search?q=cats) leave the browser, inside the encrypted tunnel.
  4. Sub-resources. The page asks for scripts, images, fonts, ads and analytics from other hostnames, and every new hostname starts its own DNS lookup. A typical page triggers dozens.

The certificate step is why DNS can redirect you but can't impersonate a site: a server that isn't really www.google.com can't present a valid certificate for it, and the browser refuses to continue.

5. My setup: Pi-hole + Cloudflare for Families

Here's what my PC's lookups go through now:

  • Firefox with DNS over HTTPS turned off, so it uses the OS like everything else.
  • Windows, with the DNS server set manually to Pi-hole for both IPv4 and IPv6. The IPv6 part matters: my ISP's router advertises its own IPv6 DNS server, and if I only changed the IPv4 setting, Windows would quietly send some lookups there and skip the Pi-hole.
  • Pi-hole on zombieboi: checks blocklists (ads, trackers, my own rules), caches, logs every query, and forwards the rest.
  • Cloudflare for Families (1.1.1.3) as Pi-hole's upstream: a recursive resolver that also blocks malware and adult sites.

Pick a scenario. The first one is the question that started this post.

Blocked ≠ doesn't exist. A blocked name comes back as 0.0.0.0 (and :: for IPv6), a deliberate "nowhere". A typo comes back as NXDOMAIN, "no such name". Firefox shows similar error pages for both, but they're different answers, and that difference is what lets software tell "blocked on purpose" from "doesn't exist".

Two things worth noticing:

  • Who blocked it matters. Ad domains are stopped by the Pi-hole itself, so Cloudflare never even sees them, and I can allowlist them. Adult sites are stopped by Cloudflare, so the Pi-hole only passes the answer along, and its allowlist can't override it.
  • Blocking happens on my own PC. Connecting to 0.0.0.0 fails instantly, locally. No packet ever goes towards the blocked site. That's also why ad blocking is invisible: a blocked ad script just quietly doesn't load.

6. Why Google locked SafeSearch

Google runs two sets of servers for search. The normal ones sit behind www.google.com. Another set sits behind forcesafesearch.google.com, and those always apply SafeSearch. Google publishes this on purpose, so schools and network operators can enforce SafeSearch with nothing but DNS.

Cloudflare for Families uses it: when asked for www.google.com, it answers with a CNAME to forcesafesearch.google.com and that name's address. My browser connects there, still asking for www.google.com, and gets back Google's genuine certificate, so nothing looks wrong. Google sees the connection arrive on its SafeSearch address and locks the setting, which is exactly the message I saw. My account settings can't override it, because the decision is made by where I connected, not who I am.

So: not Firefox, not "parent mode" detection. Just DNS pointing me at a different door of the same building.

HTTPS hides what I do on a site. DNS and SNI still reveal which sites. Encrypting Pi-hole's upstream queries (DNS over HTTPS/TLS from the Pi-hole) would hide them from the ISP too; that's a possible future project.

8. Try it yourself

On Windows (PowerShell); nslookup works the same on macOS and Linux:

nslookup www.google.com              # through your normal DNS
nslookup www.google.com 9.9.9.9      # ask Quad9 directly, no family filter
nslookup www.google.com 1.1.1.3      # ask Cloudflare for Families directly
nslookup ad.doubleclick.net          # behind a Pi-hole: 0.0.0.0 and ::
nslookup thisdoesnotexist12345.com   # NXDOMAIN ("Non-existent domain")
ipconfig /displaydns                 # what Windows has cached
Clear-DnsClientCache                 # empty Windows' DNS cache

If the third command mentions forcesafesearch.google.com and the second doesn't, you've just watched the whole mechanism from this post.

What I learned

  1. DNS is a distributed, cached tree. Most lookups never leave the house.
  2. "Which DNS server do I use?" has more answers than it looks: router defaults, manual settings, browser DoH, phone private DNS, hard-coded apps.
  3. DNS can redirect but can't impersonate, thanks to TLS certificates. That's why DNS can't show a custom block page for HTTPS sites, yet can send you to Google's SafeSearch door.
  4. Blocked (0.0.0.0) and nonexistent (NXDOMAIN) are different answers, and the difference is useful.
  5. Encryption hides content, not destinations.
