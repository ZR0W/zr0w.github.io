My Laptop Broke Its Hinge, So Now It's a Server

2026-10-14
  • homelab
  • linux
  • ubuntu
  • ssh
  • self-hosting

My Lenovo IdeaPad 5 (15ITL05) broke its screen hinge. It still boots and runs fine, but the lid flops around like it's had a long day. I could pay to fix it, or I could turn it into a headless home server that never needs to open its lid again.

Meet zombieboi: dead on the outside, alive on the inside. 🧟

This post covers what I did in one late-night session (midnight is when all good infrastructure decisions get made), what went wrong, and the commands I want to remember.

Part 1: Autopsy of the hinge

This model has a well-known weak spot. The hinge stiffens over time, and eventually opening the lid rips the hinge's brass screw inserts straight out of the plastic lid. Lenovo forum threads are full of people with the same problem.

Useful things I found:

  • Lenovo's Hardware Maintenance Manual (HMM) for "IdeaPad 5 (15", 05)" has the full teardown procedure, including hinge removal. It's on iFixit.
  • Replacement hinge set (L+R): part 5H50S28942, about $15–25 from third-party sellers.
  • Hinge covers: part 5CB0Z70212.
  • Fix options, depending on the damage: new hinges if just the hinge failed; epoxy (e.g. J-B Weld PlasticWeld, applied in layers) if the inserts pulled out but the plastic is intact; a whole new lid if the plastic is shredded.
  • Lesson: stop opening and closing a laptop with a broken hinge. Every cycle makes the damage worse.

I decided the lid can just stay closed forever instead. Problem solved. Sort of.

Part 2: Rescue the files first

Before wiping anything, I backed up the files to my main PC over Wi-Fi using LocalSend: a free app, installed on both machines, and they find each other automatically on the same network. Much nicer than wrestling with Windows file sharing.

Things people forget to back up: browser bookmarks and passwords, Desktop and Downloads, game saves hiding in AppData, and license keys.

Part 3: Installing Ubuntu Server

Making the installer

  • Downloaded Ubuntu Server 26.04.1 LTS (amd64) from ubuntu.com.
  • Flashed it to an SD card with Rufus, because I didn't have a USB stick handy.

Booting it

  • F12 at power-on opens the boot menu. The Novo pinhole button on the side is the backup plan.
  • Fun discovery: the SD card showed up as "Linpus Lite (Generic-SD/MMC/MS PRO)". Linpus is an old Linux distro, and Lenovo's firmware apparently labels a lot of Linux boot media with that name. The internal SSD showed as "Windows Boot Manager (UMIS …)". The good news: this laptop's built-in SD reader is bootable, which isn't true of every laptop.

The installer choices

  • Ubuntu Server (not "minimized", which strips tools meant for humans and is aimed at cloud images).
  • Use an entire disk on the internal NVMe SSD, with LVM. Careful: the SD card shows up as a disk too (mmcblk0), so you must pick the right one.
  • No disk encryption. A headless server can't type its own passphrase at boot.
  • Tick "Install OpenSSH server", or you're plugging a keyboard into a broken laptop forever.
  • The "Your name" field turned out to be essentially useless: it's a leftover from shared university machines, stored in /etc/passwd. I didn't give it my real name.

The Wi-Fi boss fight 🥊

The installer's Wi-Fi setup sat on "applying changes" forever, then scanning failed with:

scan failed: error triggering scan failed -100

The fix: phone USB tethering. I plugged my phone in, turned on USB tethering (which only works once the laptop is actually running, so turn it on after booting the installer), and a new usb0 interface appeared. I set it to DHCP, disabled the stuck Wi-Fi interface, and the install went through over the phone's data.

Then I set up the real Wi-Fi after installing, with netplan.

Part 4: Wi-Fi with netplan

Netplan files live in /etc/netplan/. The installer left 00-installer-config.yaml, and I added 60-wifi.yaml:

network:
  version: 2
  wifis:
    wlp0s20f3:
      dhcp4: true
      access-points:
        "MyNetworkName":
          password: "not-telling-you"
sudo chmod 600 /etc/netplan/60-wifi.yaml   # it holds a password, so lock it down
sudo netplan apply
ip a show wlp0s20f3                        # look for "state UP" and an inet address

Lesson: make sure you're using the real SSID, not a saved profile name. Windows keeps old profile names around after you rename your network. To see what's actually being broadcast:

netsh wlan show networks

(It needs location permission on newer Windows 11, for some reason.)

Part 5: Turning a laptop into a server

Don't sleep when the lid closes

The lid has a magnet sensor. A floppy broken lid will trigger it and put the server to sleep. In /etc/systemd/logind.conf:

HandleLidSwitch=ignore
HandleLidSwitchExternalPower=ignore
HandleLidSwitchDocked=ignore
sudo systemctl restart systemd-logind

Save the battery

Plugged in 24/7, a battery slowly cooks and swells. Lenovo's conservation mode caps the charge at about 60%:

echo 1 | sudo tee /sys/bus/platform/drivers/ideapad_acpi/VPC2004:00/conservation_mode

The bonus is that the battery doubles as a free UPS for short power cuts.

Firewall

sudo ufw allow OpenSSH   # ALWAYS allow this first, or you lock yourself out
sudo ufw enable
sudo ufw status

Everything incoming is blocked except what you explicitly allow. Future services each get their own ufw allow.

Part 6: SSH

Key-based login from Windows

ssh-keygen -t ed25519 -C "my-pc"
# Windows has no ssh-copy-id, so:
type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh me@zombieboi "mkdir -p ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys"

Turn on ssh-agent (as Administrator) so you don't type the key passphrase every time:

Get-Service ssh-agent | Set-Service -StartupType Automatic
Start-Service ssh-agent
ssh-add $env:USERPROFILE\.ssh\id_ed25519

And an SSH config file (~/.ssh/config), so ssh zombieboi just works. VS Code's Remote - SSH extension reads the same file:

Host zombieboi
    HostName <server-ip>
    User me
    IdentityFile ~/.ssh/id_ed25519
    ServerAliveInterval 60

The sshd_config.d gotcha 🪤

I put this in /etc/ssh/sshd_config.d/hardening.conf:

PasswordAuthentication no
PermitRootLogin no

Then I checked what sshd actually uses:

sudo sshd -T | grep -E 'passwordauthentication|permitrootlogin'

It still said passwordauthentication yes. 🤨

Why: for most options, sshd keeps the first value it reads, and the files in sshd_config.d/ load alphabetically. Another file sorted earlier was setting yes, and it won. To find the culprit:

sudo grep -ri passwordauthentication /etc/ssh/sshd_config /etc/ssh/sshd_config.d/

Lesson: never trust a config file; trust sshd -T.

In the end I decided to keep password login on. The server is only reachable on my home network, and I want to be able to log in from any device. Root login stays off. The trade-off rule: never port-forward SSH to the internet. If I want remote access, I'll use Tailscale, a private network between my own devices with no open ports.

What I learned

  1. Back up first, wipe second. Obviously. But actually do it.
  2. Laptop firmware has opinions. Boot menus mislabel things (hi, Linpus), and built-in SD readers may or may not be bootable.
  3. Installers are fragile; phones are great. USB tethering is a fantastic escape hatch when Wi-Fi refuses to work.
  4. The installer isn't the only time you can configure things. Getting through the install, then fixing Wi-Fi from a real shell with real error messages, was much easier.
  5. Config precedence is a trap. Netplan merges files (later files win); sshd takes the first value it sees (earlier files win). Always check the effective config.
  6. "Best practice" depends on your threat model. Key-only SSH matters on the internet; on a home LAN, password login plus no port-forwarding is a reasonable choice.
  7. Laptops make surprisingly good servers. They're low power, have a built-in UPS, a built-in screen for emergencies, and they're already paid for.

Best practices going forward

  • Update regularly. unattended-upgrades handles security patches automatically; run a full upgrade now and then.
  • Allow before you enable. For any firewall rule or SSH change, keep your current session open and test in a new one before logging out.
  • Use tmux for long jobs, so a dropped connection doesn't kill your work.
  • Back up your SSH private key somewhere safe, and never copy it to servers. Only the .pub goes out.
  • One key per device, so you can revoke a single device later.
  • Don't expose ports to the internet. Use Tailscale (or similar) for remote access.
  • Check temperatures occasionally (sensors), and keep the vents clear, especially with the lid closed.
  • Write things down. Hence this post.

Commands I need to learn next

Services and logs

  • systemctl status|start|stop|restart|enable <service>: manage services.
  • systemctl list-units --type=service --state=running: see what's running.
  • journalctl -u <service> -f: follow a service's logs live.
  • journalctl -p err -b: errors since the last boot.

System health

  • htop: interactive process viewer.
  • free -h: memory usage.
  • du -sh * | sort -h: what's eating my disk.
  • sensors: CPU temperatures.
  • uptime: how long since it last fell over.

Networking

  • ss -tulpn: which ports are open and which program owns them. Essential when adding services.
  • curl -I http://localhost:<port>: is my service actually responding?

Files and permissions

  • chmod / chown: permissions and ownership; most "it doesn't work" bugs start here.
  • rsync -avh src/ dest/: copying and backups done right.
  • scp file zombieboi:~/: quick copy to and from the PC.
  • find, grep -r: finding things.

Sessions and automation

  • tmux (tmux attach to reconnect).
  • crontab -e or systemd timers: scheduled jobs, for backups for example.

Containers (next adventure)

  • docker ps, docker compose up -d, docker compose logs -f, docker compose pull.
